**One rule, one repair.** A loop producing a scope denominator publishes how many iterations it

never correct is skipping *invisibly*, because it makes "this file was out of scope" and "this
fence could not read this file" byte-identical, and only one is a defect.

## The fence caught a bug in its own rule (kept, as evidence)

After repairing `check_llm_routing`, the fence still fired on it. The loop now counted
`attempted += 1` before the first skip -- the exact repair the law prescribes -- but the detector
only recognised *per-skip* discard counting. **A fence that still fires after the fix it demands
teaches the desk to ignore it.** Added `_counts_attempts_before`, requiring a literal `+= 1` or an
append: `total += price` also runs unconditionally, but a SUM cannot report members lost (pinned
by `test_a_sum_before_the_skip_does_not_excuse_the_leak`).

Then my own test caught a second over-broad rule: I had treated *any* division inside a `return`
as a scope claim, which flags `return (obs - exp) ** 2 / var` in a log-rank test. The real
`check_row_atomicity` escaped only because it assigns to `chi2` first -- so the detector was right
by accident. Rule removed; a returned ratio that is a scope claim travels in a dict with a
scope-shaped key. Verified against the pre-fix files read from `git show HEAD:` (tree untouched):
**all three still detected, precision improved.**
