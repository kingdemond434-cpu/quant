ROOT CAUSE of the 7.75x bleed: _DEFAULT_RT_BPS=4.5 is a FAIL-OPEN on unmeasured (=illiquid) symbols

FOUND BY TESTING THE EXECUTOR'S CORE ASSUMPTION, which had never been tested.

1) FUNDING PERSISTENCE (scripts/funding_persistence.py) -- does the ENTRY SIGNAL predict what the
   desk actually HARVESTS? The executor picks on CURRENT funding then holds >=24h, so what is
   earned is funding over the HOLD. Nobody had checked those are related. Same venue, same clock,
   no cross-source alignment -> the artifact class that killed mSOL/CME/bithumb is impossible here.
   RESULT -- THE SIGNAL WORKS, decisively:
     24h hold: persistence IC +0.4322 (t +29.7) | top-decile +29.08%/yr vs median +3.77%/yr
               SELECTION EDGE +25.30%/yr
     72h hold: IC +0.3781 (t +22.4) | edge +21.95%/yr
     funding shock half-life 0.8 periods (6h) -- fast-decaying shock over a persistent
     cross-sectional level, which is why 24h capture still works.
   So the strategy's core assumption is VINDICATED. Entry signal works, delta-neutrality works
   (legs +$14), and costs are the only broken component. The alpha is real; execution destroys it.

2) ROOT CAUSE OF THE COST BLEED -- traced end to end:
     _entry_gate: funding * 1e4 * periods > _rt_bps(sym)          <- correctly designed
     _rt_bps: returns the MEASURED pair round-trip, else _DEFAULT_RT_BPS
     _DEFAULT_RT_BPS = 4.5   "measured desk-median pair round-trip, used when unmeasured"
   THE DEFECT: "unmeasured" is not a random subset. A symbol is missing from the cost model
   BECAUSE IT IS TOO ILLIQUID TO MEASURE -- i.e. precisely the expensive tail. Assigning it the
   desk MEDIAN is a fail-open on the worst names. The executor's own docstring records the truth:
   NOMUSDT realised -149bps, KNCUSDT -211bps. So symbols plausibly costing 100-200bps are being
   gated at 4.5bps -- a 20-40x under-estimate, applied selectively to the worst books.
   CONFIRMED LIVE: 3 of the 4 open carries (1000CATUSDT, MOVEUSDT, TSTUSDT) are NOT in the cost
   model and are running on the 4.5bps default. Only COOKIEUSDT is measured (at 59bps, itself
   flagged degenerate).
   This is the same fail-open pattern found three times today (activation gate, budget guard,
   health dashboard): the ambiguous branch PERMITS instead of blocking.

   FIX (specified, NOT applied -- this is live order-placing code and my defect rate today is too
   high to touch it): _rt_bps must fail CLOSED. Unmeasured => use a PESSIMISTIC prior (e.g. the
   90th percentile of measured costs, ~20bps from today's 30-symbol run) or refuse the open
   entirely until measured. One constant, and it converts the entry gate from decorative to real.
